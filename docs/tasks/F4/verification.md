## Found while verifying

- **A 401 to a POST was a network error inside Next.js.** With the dev server, `Prefer: code=401` on
  login answered `503 SERVICE_UNAVAILABLE` ("fetch failed: expected non-null body source") while the
  same handler in Vitest, and plain Node `fetch`, answered 401. Next's patched `fetch` rebuilds a
  `Request` whose body stream has lost its source, and the fetch standard turns any 401 answer to such a
  request into a network error. Every POST that can be refused with 401 — wrong password, refused
  refresh, expired token on logout — was affected; GETs (`/v1/me`) were not, which is why it was
  missed. Fixed in `39598f6`: `upstream()` sends `fetch(url, init)` with a string body (`sendPlain`).
  Regression: `auth.spec.ts` › "a wrong password is refused in the API's own terms".
- **`next build` must not need `SESSION_SECRET`.** The first production build failed because the
  secret was demanded at module load under `NODE_ENV=production`. It is now read lazily and checked by
  `instrumentation.ts` when a server starts (plan decision 5 updated).
- Chrome logs a refused fetch as a console error; the two refusal screens allow exactly those lines.

## Gaps

- **Stray edits in this checkout.** While F4a was being verified, uncommitted changes appeared in
  `src/config/constants.ts`, `src/lib/api/mock/fixtures.ts`, `src/lib/api/mock/repository.ts`,
  `src/lib/server/catalogue.ts`, `tests/unit/realtime.test.ts` and a new
  `tests/unit/live-simulation.test.ts` (a live-match simulation in the mock fixtures). They are not
  F4a's and were not committed on this branch; the dev server the screens were taken from includes
  them (the "Live simulation" sections in the full-page PNGs). Two of them failed Prettier, which made
  `pnpm verify` exit 1 as a single command; they were formatted in place (whitespace only, not staged)
  so the gate could run end to end. Risk: none to F4a's behaviour; their owner decides what happens to
  them.
- **Prism cannot answer a real token lifecycle.** Refresh-on-expiry and the refused refresh are proven
  with a stubbed upstream (route and loader tests), not live; Prism always answers the login example.
- **Refresh deduplication is per process.** With several replicas (C18 §7) two servers may refresh the
  same token at once and trip C01 §8's reuse detection; follow-up for the backend (a short reuse
  grace window). Not reproducible locally.
- **Contract request 004** (`X-Client-IP`, `X-Client-Device`) is `proposed`: the address is read, not
  sent. `Auth` must not join `API_REAL_TAGS` before it lands (as the request says).
