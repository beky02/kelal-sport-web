# F6b — plan

Plan gate: approved 2026-10-03 (mode: interactive) — question 2: the proposed status copy, DEP-09
line included; question 3: a new key after `PAY_PROVIDER_ERROR`; question 4: contract request 009 written now.

## Understanding

The wallet's deposit flow still runs on the in-repo mock: methods are a fixed list with float limits, the
amount is a whole-birr `number`, "Confirm and pay" calls a mock that invents a reference, and a fake
status poll flips between pending, success and failed. F6b moves deposits onto the contract: methods and
their deposit limits from `GET /v1/payment-methods`, a deposit started with `POST /v1/deposits` through a
new route handler that forwards the browser's `Idempotency-Key`, and a status screen driven by what the
API says next (`next_action`): leave for an allow-listed provider page, approve the push on the phone,
or choose another method when the web can't finish it. That screen polls `GET /v1/deposits/{id}` every
3 s until the deposit reaches a final status. The balance and history are only re-read, never adjusted,
and only once the server says `completed`. A deposit with no answer is retried with the same key, so a
dropped connection never starts a second one. Each refusal the contract lists says what happened and
offers its fix.

## Design

**Contract → loader → mapper → route → api → hook → components**

- `src/lib/server/config.ts`: `paymentRedirectHosts` (decision 6); `isAllowedProviderUrl(url, hosts)`
  (pure, exported for the unit test).
- `src/lib/server/payments.ts` (server only), tag `Payments`:
  - `loadPaymentMethods(ctx, session)` → `GET /v1/payment-methods` → `toPaymentMethods`.
  - `createDeposit(ctx, session, request, key)` → `POST /v1/deposits` with `Idempotency-Key` and
    `toDepositRequest(request, returnUrl)` → `toDeposit(deposit, allowed)`. A refresh re-sends the same
    key (as `placeBet`).
  - `loadDeposit(ctx, session, id)` → `GET /v1/deposits/{id}` → `toDeposit(deposit, allowed)`.
- `src/lib/api/mappers/payments.ts` (pure): `toPaymentMethods(list)` (strings untouched, unknown codes
  left out, `withdrawal ?? null`); `toDepositRequest(request, returnUrl)`; `toDeposit(deposit,
isAllowed)` — `next_action` → `redirect { url }` only when `isAllowed(url)`; `ussd_push { message }`;
  anything else → `unsupported { reason: "app_sdk" | "redirect_refused" | "unknown" }`;
  `failure_reason`, `expires_at`, `completed_at` → `null` when absent.
- Route handlers:
  - `GET /api/payment-methods`: a session for this tenant (401), read-only so no CSRF, `no-store`,
    Prism's `Prefer` in `next dev` only.
  - `POST /api/deposits`: `assertSameOrigin` (origin, CSRF header, JSON); a UUID `Idempotency-Key`
    (400, never made here); a 4 KiB body checked by a strict schema — `method` one of the contract's
    codes, `amount` the contract's `Money` above zero, nothing else (422); a session (401); 201 with the
    mapped deposit, or the API's Problem.
  - `GET /api/deposits/[id]`: an id that can be one (`^[A-Za-z0-9_-]{1,64}$`, as `/api/bets/[id]`) or
    404 with nothing sent; a session; `no-store`.
- `src/lib/api/schemas.ts`: `paymentMethodSchema`, `paymentMethodsSchema`, `depositSchema` (the redirect
  URL must be `https:`), `depositRequestSchema` (strict), each `satisfies z.ZodType<Domain>`;
  `paymentResultSchema` keeps the withdrawal mock (amount a string).
- Domain types (`features/wallet/types`): `PAYMENT_METHOD_CODES`, `PaymentMethodCode`, `AmountRange`,
  `PaymentFlow`, `PaymentMethod { code, name, flow, available, deposit, withdrawal }`,
  `DEPOSIT_STATUSES`, `DepositStatus`, `DepositNextAction`, `Deposit { id, method, amount, status,
nextAction, failureReason, expiresAt, createdAt, completedAt }`, `DepositRequest { method, amount }`.
  The mock `PaymentMethod` (`id`, `mono`, `kind`, number limits) goes.
- `src/lib/query/keys.ts`: `paymentKeys.all`, `.methods(lang)`, `.deposit(id)`; `forgetPlayer` drops
  `paymentKeys.all`.
- Browser API `src/features/wallet/api/payments.ts`: `getPaymentMethods`, `createDeposit(request, key,
deadline)` (30 s, as placing), `getDeposit(id)` (id encoded).
- Hooks `src/features/wallet/hooks/use-deposit.ts`: `usePaymentMethods(enabled)`; `useDeposit(id)` —
  polling, invalidation on completion (decision 12); `useDepositAttempt(owner)` — the intent: `confirm`
  (new key, or Try again while unanswered with the same method and amount), `retry`, the outcome
  (`sending`, `unanswered`, `refused`, `answered`), seeding the deposit's query with the 201.
- Pure lib `src/features/wallet/lib/deposit.ts`: `amountProblem(amount, range)`, `isFinal(status)`,
  `shouldPoll(deposit)`, `depositOutcome(error)` (unanswered / session / refused), `depositRefusal(error,
method, amount)` → `{ title, body, detail, fix }`; `src/features/wallet/lib/provider-redirect.ts`:
  `goToProvider(url)` (`https:` only, `window.location.assign`), `rememberDeposit`, `rememberedDeposit`,
  `forgetDeposit` (sessionStorage).
- Components:
  - `WalletView`: guest / loading / error as now; then home, `DepositFlow` (keyed by the player) or
    `WithdrawFlow`; `?action=deposit|withdraw` as now; `?deposit=return` resumes (decision 8).
  - `DepositFlow` (new): method → amount → confirm → status.
  - `MethodStep`: the contract's methods by mode; loading, couldn't load (Try again), none available;
    unavailable tiles disabled with their reason.
  - `AmountStep`: string amount; the method's range for the mode; above-maximum message; the withdrawal
    ceiling (`cash`) as now.
  - `ConfirmStep`: rows by mode (decision 5); the refusal with its fix; the no-answer alert with Try again.
  - `DepositStatus` (new): decision 10, `role="status"` so changes are announced, focus on the heading
    when it opens.
  - `WithdrawFlow` (new; the mock flow moved out of `WalletView`), `PaymentResultStep` (withdrawals only).
- **Errors**: decision 14; methods: 401 → session watcher, anything else → couldn't load + Try again;
  a deposit read: decision 12.
- **i18n** (en and am): a `deposit` namespace — flow lines, unavailable, methods failed / none, the web
  prompt, the no-answer alert and Try again, the refusal titles, bodies and fix labels, every status
  title and body (question 2), Continue to {method}, Back to wallet, Choose another method, couldn't
  check / not found, the status words; `wallet.aboveMaximum`. Removed: `wallet.mobileMoney`,
  `wallet.gateway`, `wallet.failedBody`, `wallet.cancelPayment` (withdrawals get Back to wallet too).
  Composed Amharic in `TRANSLATION-NOTES.md`.
- **Flags**: none.

## Risks

- **Money**: no deposit is optimistic and no balance is computed or patched: the balance and history are
  re-read (invalidated) only when the server says `completed`, and shown as sent. Amounts are strings
  end to end; the only comparisons are `compareMoney` against the method's range and the withdrawal
  ceiling. One key per intent, the same on a retry after no answer, so a dropped connection or a
  refreshed session can't start a second deposit; the route handler forwards and never makes one.
- **Security**: the open redirect is the new risk — closed by the server-side allow-list (exact
  hostnames, https, default port, no user info, fail closed in production), re-checked in the browser
  (`https:`); `return_url` is built on the server from the tenant's own origin. `POST /api/deposits`
  has the same gates as `POST /api/bets` (origin, CSRF header, JSON, 4 KiB, strict schema, UUID key,
  session); ids are checked before they go into an upstream path; `no-store`; `Prefer` in `next dev`
  only and never to the real API. `sessionStorage` holds only a deposit id and a player id.
- **Accessibility**: the status screen is `role="status"` (each change announced), refusals and the
  no-answer alert are `role="alert"`, focus moves to the status heading; disabled tiles say why in text;
  44 px targets; no `uppercase` or `tracking-*` on labels (the old badge had both).
- **Performance**: one small read every 3 s, only while the deposit is open, unfinished and the tab is
  visible; methods are cached per player and language for 30 s.

## Out of scope

- Card payments; paying from another phone (`phone`); a list of pending deposits (not in the contract).
- Withdrawals and payout accounts beyond the new method shape (F6c).
- The deposit-limit card and the deposit-limit dialog's figures (F7, `/v1/me/limits`).
- Brand logos on the tiles (not in the contract).
