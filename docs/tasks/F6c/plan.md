# F6c — plan

Plan gate: approved 2026-10-03 (mode: interactive) — question 2: the proposed copy; question 3: payout
accounts added and removed in the withdraw flow's account step; question 4: contract request 010 written now.

## Understanding

Withdrawals still run on the in-repo mock: "Confirm withdrawal" calls a mock that invents a reference,
a fake poll flips between pending, success and failed, the account is a hard-coded `+251 9•• ••• 482`,
and the confirm step shows a fee and a "You receive" figure the API never sent. F6c moves money out onto
the contract: the player picks a method with a `withdrawal` range, then one of their saved payout
accounts (`/v1/me/payout-accounts`, which they can also add to and remove from) or a new number, then
an amount checked against the method's range and the cash balance as strings; `POST /v1/withdrawals`
goes through a new route handler with the browser's `Idempotency-Key`, so a dropped connection never
asks for a second withdrawal. The status screen shows what the API decided — every `WithdrawalStatus`,
the review and rejection reasons — offers Cancel only while the withdrawal is `requested` or in
`review`, and is reachable again from the withdrawal's row in the history. The balance moves only when
the API answers: it is re-read, never adjusted. Each refusal the task lists says what happened and
offers its fix.

## Design

**Contract → loader → mapper → route → api → hook → components**

- `src/lib/server/withdrawals.ts` (server only), tag `Payments`, every call through `withSession`:
  - `loadPayoutAccounts(ctx, session)` → `GET /v1/me/payout-accounts` → `toPayoutAccounts`.
  - `addPayoutAccount(ctx, session, request)` → `POST /v1/me/payout-accounts` with
    `toPayoutAccountCreate(request)` → `toPayoutAccount`.
  - `removePayoutAccount(ctx, session, id)` → `DELETE /v1/me/payout-accounts/{id}` (204).
  - `createWithdrawal(ctx, session, request, key)` → `POST /v1/withdrawals` with `Idempotency-Key` and
    `toWithdrawalRequest(request)` → `toWithdrawal`. A refresh re-sends the same key (as deposits).
  - `loadWithdrawal(ctx, session, id)` → `GET /v1/withdrawals/{id}`; `cancelWithdrawal(ctx, session, id)`
    → `DELETE /v1/withdrawals/{id}` → `toWithdrawal`.
- `src/lib/api/mappers/withdrawals.ts` (pure): `toPayoutAccounts` (a provider code the contract adds
  later is left out, as methods), `toPayoutAccount`, `toPayoutAccountCreate` (`{ provider, account_ref }`),
  `toWithdrawalRequest` (`payout_account_id` or `account`, never both), `toWithdrawal` (absent
  `account_masked`, reasons and `paid_at` → `null`).
- Route handlers (each: a session for this tenant or 401 with nothing sent, `no-store`, Prism's `Prefer`
  in `next dev` only and never to the real API):
  - `GET /api/payout-accounts`; `POST /api/payout-accounts`: `assertSameOrigin`, a 4 KiB strict body
    `{ provider, account }` — a contract method code and a `Phone` — else 422 with nothing sent; 201.
  - `DELETE /api/payout-accounts/[id]`: `assertSameOrigin({ json: false })`, an id that can be one
    (`^[A-Za-z0-9_-]{1,64}$`) else 404 with nothing sent; 204.
  - `POST /api/withdrawals`: `assertSameOrigin`; a UUID `Idempotency-Key` (400, never made here); a 4 KiB
    strict body `{ method, amount, to }` — `amount` the contract's `Money` above zero (`abort`, so a
    malformed one is 422 not 500), `to` either `{ kind: "saved", payoutAccountId }` (an id that can be
    one) or `{ kind: "new", account }` (a `Phone`), nothing else; 201.
  - `GET /api/withdrawals/[id]`; `DELETE /api/withdrawals/[id]` (`assertSameOrigin({ json: false })`):
    the id check, as above.
- `src/lib/server/csrf.ts`: `assertSameOrigin(request, { json = true })`.
- `src/lib/api/patterns.ts`: `PHONE_PATTERN`, the contract's `Phone`. `src/lib/api/schemas.ts`:
  `payoutAccountSchema`, `payoutAccountsSchema`, `payoutAccountRequestSchema` (strict),
  `withdrawalSchema`, `withdrawalRequestSchema` (strict), each `satisfies z.ZodType<Domain>`;
  `paymentResultSchema` goes.
- Domain types (`features/wallet/types`): `PayoutAccount { id, provider, accountMasked, holderName,
verified, createdAt }`, `PayoutAccountRequest { provider, account }`, `WITHDRAWAL_STATUSES`,
  `WithdrawalStatus`, `Withdrawal { id, method, amount, status, accountMasked, reviewReason,
rejectionReason, createdAt, paidAt }`, `WithdrawalDestination` (`saved` | `new`),
  `WithdrawalRequest { method, amount, to }`; `FlowStep` gains `account`; `WITHDRAW_FLOW`;
  `PaymentResult` goes.
- `src/lib/query/keys.ts`: `paymentKeys.payoutAccounts()`, `.withdrawals(id)` (every language's copy of
  one), `.withdrawal(id, lang)`. All under `paymentKeys.all`, which `forgetPlayer` already drops.
- `src/config/routes.ts`: `withdrawal(id)` → `/wallet?withdrawal={id}` (encoded).
- `src/lib/api/client.ts`: `apiClient.delete`; the CSRF header on every non-GET.
- Browser API `src/features/wallet/api/withdrawals.ts`: `getPayoutAccounts`, `addPayoutAccount`,
  `removePayoutAccount` (204 → `z.undefined()`), `createWithdrawal(request, key, deadline)` (30 s, as

- Store `src/features/wallet/stores/withdrawal.store.ts`: `{ owner, sending, unanswered, unseen }` and

- Pure lib `src/features/wallet/lib/withdrawal.ts`: `WITHDRAWAL_POLL_MS`, `REVIEW_POLL_MS`, `isFinal`,

  - `TransactionRow`: decision 14.
  - Deleted: `PaymentResultStep`.
- **Errors**: decisions 11, 12, 13, 18; accounts and a withdrawal read: 401 → the session watcher,

## Risks

- **Money**: no withdrawal or cancel is optimistic and no balance is computed or patched: the wallet and
  history are re-read after every answer that may have moved money (a 201, a cancel's 200, any status
  change). Amounts are strings end to end; the only comparisons are `compareMoney` against the method's
  range and the cash balance. One key per intent, the same on a retry after no answer (including a 502),
  so a dropped connection or a refreshed session can't request a second withdrawal; the route handler
  forwards and never makes one. The confirm step shows a new number in full, so money doesn't go to a
  typo, and claims no fee, net amount or arrival time.
- **Security**: four new mutating route handlers with the existing gates (origin, CSRF header, JSON for
  the POSTs, 4 KiB strict bodies, a UUID key on the withdrawal, the session); ids checked before they go
  into an upstream path; `no-store`; `Prefer` in `next dev` only. The `?withdrawal=` id is opaque and
  checked by the route handler; another player's is the API's 404. Phone numbers are never logged.
- **Personal data**: accounts and withdrawals under `paymentKeys`, dropped on every session change; the
  flow, the store and the withdrawal screen are the signed-in player's alone.
- **Accessibility**: the status screen is `role="status"` with focus on its title; refusals and the
  no-answer alerts `role="alert"`; the accounts are a radio group; Remove's question takes focus and
  gives it back; busy buttons stay focusable (`aria-disabled`); 44 px targets; no `uppercase` or
  `tracking-*` on labels (the mock's badge had both).
- **Performance**: one small read every 10 s (60 s in review), only while a withdrawal's screen is
  open, unfinished and visible; accounts cached per player for 60 s and re-read after each change.

## Changes during implementation

- **Steps 4–6 landed as one commit** (`28a265e`): the account step, the confirm step's attempt and the
  status screen are one flow (`WithdrawFlow`), which compiles only whole, as F6b's steps 1–6. The
  strings landed with step 3, whose lib names their keys.
- **Files beyond the list**: `src/features/auth/lib/phone.ts` (`formatPhone`, the new number in full on
  the amount and confirm steps, beside the existing `maskPhone`). `src/lib/api/patterns.ts` also holds
  `API_ID_PATTERN`, the id check the four route files and the withdrawal body's `payoutAccountId` share.
- **The status screen reads the method names itself** (`usePaymentMethods`) rather than taking a lookup:
  it is used from the flow and from `?withdrawal=`.
- **The stored attempt keeps the account as the confirm step showed it** (`accountLabel`), so a
  withdrawal reopened on Try again names its account; the request itself carries only the id or number.
- **A withdrawal to a new number marks the accounts stale** rather than reading them at once: the list is
  not on screen after a 201, so it is read again the next time it is shown, however fresh it was.
- **Cancel's "too late" is by code**: only `PAY_WITHDRAWAL_NOT_CANCELLABLE` reads as too late; another
  409 shows the API's title. Every refused or unanswered cancel reads the withdrawal again.
- **`pnpm ui`**: 27 withdrawal screens (the plan's list plus `withdraw-methods`, `withdrawal-cancelled`
  and `withdrawal-cancel-unconfirmed`); `wallet-held` re-taken for the withdrawal row's chevron.
